# Stripe operations and verification

The implementation uses `stripe@23.1.0`, whose generated default API version is `2026-10-28.endive`. It creates Connect accounts through Accounts v2 and uses the documented v1 compatibility endpoints for their balances and payouts. Server credentials are Cloudflare secrets; no client code receives secret keys, identity documents or bank details.

Production paid bookings remain disabled while Connect configuration, the connected-account payout webhook and provider acceptance remain incomplete. The restricted live API key and platform webhook secret are installed; the operator has approved the Connect responsibility acknowledgement. See [VERIFICATION.md](VERIFICATION.md) for the latest configuration evidence. The listings pilot can accept posts and applications with `LISTINGS_ENABLED=true` and `LAUNCH_MODE=preview`; those settings do not permit hiring, work progression, Checkout or payouts.

The financial regression tests use a provider fixture, real D1 through Miniflare, and Stripe's real webhook signature verifier. An isolated temporary Stripe sandbox was also probed on 2026-11-04. Actual provider acceptance covered an unpaid CAD platform Checkout session, an identical idempotent replay, retrieval and expiry, plus creation, disabling and deletion of a snapshot webhook endpoint. The endpoint used a reserved `.invalid` target, so no webhook delivery was tested. Accounts v2 recipient creation returned **403: the sandbox credential lacked Accounts v2 access**. That rejection occurred before recipient payload validation. No connected account, destination charge, application fee, refund or payout was tested, and no money moved. The local redacted evidence is in `.local/stripe-provider-acceptance.json`, excluded from the public repository.

The anonymous sandbox expires after seven days and is not the managed staging environment. Complete the account claim/setup or provision an appropriate managed Canadian sandbox with Connect access before the acceptance checklist below. Basic platform Checkout acceptance does not establish marketplace acceptance.

## Configuration

1. Create the Canadian business's Stripe platform and complete its Connect setup, identity, business and banking requirements. Choose the supported marketplace configuration and confirm fee/loss responsibility with Stripe.
2. Create an isolated Canadian sandbox with Accounts v2 and Connect access for staging. Set `APP_ENV=staging`, `LAUNCH_MODE=live` only on the isolated staging Worker, and install test-mode secrets. Staging rejects live keys; production rejects test keys. The `live` launch-mode flag enables marketplace routes, while Stripe's key mode determines whether provider operations are test or real. Keep staging data, webhooks and credentials separate from production.
3. Install `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and `STRIPE_CONNECT_WEBHOOK_SECRET` with `wrangler secret put` or secure CI secret management. Do not put credentials in the repository or paste them into support messages.
4. Configure a platform-account **snapshot webhook** at `/api/webhooks/stripe` for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.updated`, `charge.dispute.closed`, `refund.created`, `refund.updated` and `refund.failed`.
5. Configure a connected-account **snapshot webhook** at `/api/webhooks/stripe-connect` for payout events, including `payout.created`, `payout.updated`, `payout.paid`, `payout.failed` and `payout.canceled`. Each endpoint needs its own signing secret. This handler does not consume Accounts v2 thin-event notifications; account readiness is read from Stripe on demand.
6. Enable eligible debit-card collection in Connect external account settings if offering Canadian Instant Payouts, and bank-account collection for standard payouts. Confirm the platform's daily instant limit and pricing. Keep payout application-fee pricing at zero for the launch model: SaladFinder absorbs payout fees through its client service fee.
7. Set the verified production `APP_URL`, real support identity, approved terms and applicable tax configuration. Complete the business decisions in [research.md](./research.md) and the launch checklist before opening real bookings.

The owner must configure which payment methods Checkout presents. The application permits Stripe's dynamic selection; bank-debit and other asynchronous methods cannot promise immediate availability. Local development can use a test key; it never substitutes a fake provider automatically. Without the required secrets, money routes return 503.

## Flow and records

A client approves a milestone, then pays its worker amount plus `max(CA$3, 12% + CA$1)` through hosted Checkout. The shared `feeCents` function is used by server and client. The server stores the exact request payload and idempotency key before calling Stripe; a request retry uses that payload, even if application settings change. One milestone can have another attempt only after the prior Checkout session is definitively expired.

The redirect from Checkout merely returns the client to the job. A signed webhook verifies the canonical PaymentIntent, paid amount, currency, fee, destination, metadata and mode before updating the ledger. Full refunds take precedence over late success notifications. Refunds and disputes delivered before Checkout success are linked through canonical PaymentIntent metadata. Payout notifications retrieve current Stripe state to prevent stale events from regressing the ledger.

`payment_attempts`, `payout_intents`, `refund_intents`, `connect_intents`, `stripe_events` and `payment_incidents` preserve operational evidence. Do not manually delete an unresolved intent to “unstick” a payment: that can remove the duplicate-payment guard.

The app supports full admin refunds, reversing the worker transfer and application fee. Refund initiation is not always refund completion. Pending or failed provider refunds require reconciliation; a refund after funds leave the connected account can create a liability for the platform. Partial refunds performed in Stripe are treated as disputes for manual review rather than silently treating the milestone as unpaid.

## Holds and limitations

Reporting by a job participant blocks new checkouts and in-app payout requests for that worker while the job is disputed. Stripe disputes and unresolved refund operations also prevent in-app payouts; restoring a local report does not clear those financial restrictions. SaladFinder attempts to expire known open Checkout sessions and checks the job again after creating a session. If a payment completes concurrently, the ledger records the payment and an incident for review.

**This is not escrow or a bank-level freeze.** Destination charges immediately move the worker share to the connected Stripe account. An in-flight charge, an already initiated payout, a Stripe automatic payout or a payout initiated in the worker's Stripe dashboard is not recalled by a SaladFinder report. Never describe these controls as guaranteeing that disputed funds remain available. The operator needs a dispute process and a funded reserve.

## Worker payout choices

Readiness is determined from the Canadian Accounts v2 recipient's active `stripe_transfers` and `payouts` capabilities. Requesting transfers creates the Stripe balance; Stripe automatically requests its payouts capability. The app reads the current capabilities, external destinations and balance before offering or submitting a payout. Completing onboarding alone is insufficient. See [Accounts v2 payouts capability](https://docs.stripe.com/changelog/basil/2025-04-30/payouts-are-now-a-capability).

- **Instant is selected by default when eligible.** For Canada the supported instant destination is an eligible debit card. The API matches expanded `instant_available.net_available` to that destination's `available_payout_methods` and never sums destinations that share the same balance. A missing or insufficient eligible net balance disables instant requests. The supported per-request range is CA$0.60–CA$9,999. Stripe describes arrival as typically within 30 minutes, including weekends and holidays; account restrictions, daily limits and delays still apply. This is not a guarantee of same-day bank arrival. See [Connect Instant Payouts](https://docs.stripe.com/connect/instant-payouts).
- **Standard bank payout remains an explicit choice.** The app requires sufficient available CAD, a usable linked CAD bank account that supports standard payouts, and manual payout scheduling. It passes that bank destination explicitly, avoiding Stripe's default-destination selection. The app's standard request range is CA$1–CA$9,999; these are product limits. Settlement, first-payout checks and bank processing can delay arrival. See [payout creation](https://docs.stripe.com/api/payouts/create) and [payout timing](https://docs.stripe.com/payouts).
- **Payout setup is user initiated.** Choosing the setup/onboarding action sets the connected account's schedule to manual through Balance Settings, then opens Stripe-hosted onboarding. A status read does not change the schedule. If the worker later changes scheduling in Stripe, standard requests require setup again. Instant availability is evaluated independently; an automatic schedule alone is not described as making instant payouts impossible. See [payout schedules](https://docs.stripe.com/connect/manage-payout-schedule).

Manual scheduling creates an operator obligation: Stripe's maximum holding period for Canadian balances is **90 days**. Before enabling paid bookings, establish a daily review of outstanding balances and their age, reminders and escalation well before that deadline, and a documented payout/reconciliation path for inactive workers or restricted accounts. The app does not automatically sweep aging balances or provide that external monitoring. An app dispute flag cannot justify holding funds indefinitely. See [manual payouts](https://docs.stripe.com/connect/manual-payouts).

SaladFinder's proposed pricing absorbs processing and payout fees rather than deducting an additional payout charge from the displayed worker amount. Stripe currently lists an additional 1% platform fee for Connect Instant Payouts; the platform's other Connect and payment fees still apply. Confirm the actual account's pricing and limits before paid launch. See [Canadian Connect pricing](https://stripe.com/en-ca/connect/pricing).

## Retry safety

Each payout has a durable request identifier, account, amount, method and destination. The browser preserves the current request across reloads, and the status API returns an unresolved server intent for recovery. A timeout, rate-limit response before reconciliation, uncertain database result or ambiguous provider error does not authorize a new request identifier. Retry the same operation or reconcile it with support. Only a confirmed rejection before creation releases the form to begin a new operation; the server records that decision atomically to prevent a concurrent submission from creating the original payout.

An ambiguous create request remains retryable only within a conservative 23-hour window. Stripe may prune idempotency keys after their retention period, so the app refuses an uncertain old request instead of risking another charge. A known asynchronous payment failure is held for support reconciliation; the current UI does not automatically generate a replacement for it. Repeated deterministic provider failures can likewise require support to clear an intent after confirming no money operation was created. See [idempotent requests](https://docs.stripe.com/api/idempotent_requests) and [low-level error handling](https://docs.stripe.com/error-low-level).

## Reconciliation runbook

1. Locate the job, milestone and intent in D1; use its Stripe identifier or idempotency key to locate the exact provider request. Do not use customer names or amount alone to infer identity.
2. Compare Stripe's canonical object and request logs with the expected amount, CAD currency, recipient, application fee and metadata. For a missing response, determine whether the provider created an object before making any new request.
3. Redeliver the relevant Stripe webhook after fixing a transient failure. Signature failures or mismatched amount/destination return a non-2xx status; do not bypass those validations to clear a retry queue.
4. Review `payment_incidents`, failed or pending payouts, refunds and disputes. Confirm bank arrival through Stripe's payout evidence; a Checkout success is insufficient.
5. If manual intervention is required, preserve an audit record identifying the operator, provider evidence, original intent and exact repair. An old ambiguous intent must be reconciled before a replacement operation is issued.
6. Review Stripe's dashboard, outstanding balance ages and webhook delivery health daily during a controlled paid pilot. Escalate balances approaching the Canadian manual-payout holding limit before it expires. The current app has an admin review interface, but does not supply an external on-call alerting service, aging-balance automation or an automated dispute-evidence submission system.

## Acceptance before enabling production money

Run `npx vitest run tests/payments.test.ts` for the local financial regression suite. Then, with a managed Stripe sandbox that has Connect access, verify Canadian recipient creation, hosted onboarding, active v2 capabilities, debit-card and bank destinations, user-initiated manual scheduling, destination Checkout including 3DS, delayed success/failure, duplicate and reordered webhook delivery, checkout expiry, full refund, dispute, standard payout failure, instant eligibility rejection and retry recovery after a lost response or browser reload. Confirm the actual fee, destination and ledger values for each operation. Use the Stripe CLI's webhook forwarding or deployed staging endpoints; keep platform and Connect signatures separate.

After those checks, a small explicitly authorized real transaction and bank payout are still required to verify the production integration and actual payout timing. The business's tax, reporting, legal classification, support operations and cash reserve are separate launch requirements that cannot be proven by automated tests.
